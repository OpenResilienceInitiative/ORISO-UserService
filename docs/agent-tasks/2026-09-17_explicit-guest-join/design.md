# Explicit guest Join: implementation contract

Issue: OpenResilienceInitiative/ORISO-UserService#1183. Prerequisite: OpenResilienceInitiative/ORISO-UserService#1182. This branch is based on its reviewed additive contract; the eventual PR targets dev and must retain that dependency.

## Required behavior

The selected server-known identity is created only after Join. A client-generated, cryptographically random retry capability binds the invitation, original selection and a persisted actual candidate. Repeated requests must recover the same logical user/session across replicas and restarts. There are no plaintext stored passwords or tokens. Reuse with changed input conflicts. Unknown provider outcomes never permit choosing another name.

The attempt must commit before external writes. Claims serialize workers; ownership is revalidated after ambiguous writes. Provider names are immutable once their create step begins. Completed session association and local session creation need an atomic local transaction or equivalent unique association. Ended sessions, disabled identities, revoked/expired invitations and terminal attempts must not be resurrected.

## Verified helper limitations

- `CreateAnonymousEnquiryFacade` chooses its own name and random password.
- `AnonymousUserCreatorService` and `AnonymousConversationCreatorService` perform rollback unsuitable for durable retry.
- `CreateUserFacade.provisionMatrixUser` generates a new random password on each call.
- `MatrixSynapseService.createUser` reactivates deleted identities on `M_USER_IN_USE`; the new Join must use a create-only adapter instead.
- `MatrixSynapseService.loginUser` can return a cached token keyed by username without checking the supplied password. Ownership proof must be uncached, check the returned Matrix user ID, and clean up its temporary token/device.
- Keycloak ownership metadata must be part of the initial create payload, not a follow-up attribute write. A retry cannot use only a username match as proof.

Existing redeem and account-creation helpers retain their behavior during this additive implementation. Reusing their unsafe orchestration is prohibited; focused repository, consent and identity primitives may be reused within the new transaction/ownership contract.

## Pending collision protocol: independently reviewed handoff constraint

The original specification requires at most three actual candidate attempts and replacement only after a definite name collision. The existing generic pending phases are insufficient evidence: a concurrent retry could create the account between committed intent and initial dispatch, causing the initial caller to receive a conflict against its own account. Do not implement automatic replacement directly on the current ConflictException catch.

Selected protocol (initial permit/reconciliation slice implemented below; candidate replacement still NOT IMPLEMENTED): bind an initial in-memory dispatch permit to candidate ordinal/generation after intent commits. Hold the attempt row lock while validating that permit, dispatching and persisting its outcome. Before any repeated provider write, a caller without that permit must independently commit an irreversible RECONCILING state which revokes initial collision authority. A delayed initial caller then fails permit validation. Once reconciling, later conflicts remain unknown and cannot authorize a replacement. Failed database transactions cannot regain collision authority through a new transaction. This conservative rule may lose replacement availability when a permit is lost before dispatch, but preserves same-candidate recovery and avoids duplicate identities.

Matrix ownership proof and create responses must remain separate; `ensureOwned` alone hides the necessary outcome provenance. Only after a safely persisted Matrix collision and confirmed cleanup of the owned provisional Keycloak account may one atomic transaction archive the prior candidate metadata and bind the next actual name/avatar. Keep the original client request binding, no more than three candidates, and no plaintext secrets. Unknown cleanup retains the old candidate. Tests must cover both handoff orderings, lost provider/DB responses, rejected stale permits, and no replacement after an earlier unknown write.

A new provider cleanup primitive is being added first. Five HTTP contracts compile-failed before `deleteOwned` existed (`/tmp/r4-owned-cleanup-red.log`). It checks exact owned active identity before DELETE and requires absent readback; missing-on-retry is idempotent, foreign/disabled accounts are refused. All 16 Keycloak HTTP contracts passed with Maven exit 0 (`/tmp/r4-owned-cleanup-green.log`). Independent read-only review found no concrete defect in this primitive. This primitive is not called by Join yet and does not claim complete compensation/replacement.
